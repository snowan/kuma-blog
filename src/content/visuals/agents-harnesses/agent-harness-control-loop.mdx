## How to read the loop

The model is one participant in the system. It receives context and proposes the next response or tool call. Four surrounding transitions determine whether that proposal becomes dependable work:

1. **Intent** records the requested outcome, constraints, and granted authority.
2. **Proposal** asks the model for one next action using the available tool schemas.
3. **Policy** validates the tool, arguments, scope, and consequence before anything changes.
4. **Execution** runs the approved action in a bounded environment and records the result.
5. **Evidence** compares the environment with the completion contract.

Evidence can end the run, support a bounded repair attempt, or produce a clear human decision. It should not be collapsed into the model saying “done.”

## The two boundaries

The diagram emphasizes two checks that are easy to blur:

| Boundary | Question | Example |
| --- | --- | --- |
| Authorization | Is this action allowed now? | May this run publish the generated site? |
| Verification | Did the requested outcome occur? | Does the hosted route serve the exact tested commit? |

Authorization without verification permits actions but cannot prove success. Verification without authorization may prove that a change occurred while ignoring whether the system had permission to make it.

## What returns to the next call

When the run continues, the harness should return structured state:

- the tool result or typed error;
- its provenance and artifact reference;
- remaining budget;
- unresolved completion checks;
- any authority that is still missing.

This is why an append-only event log is more useful than conversation text alone. The log gives context assembly, recovery, audit, and evaluation one shared history.
